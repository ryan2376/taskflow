Part 1 — Two apps, one system

TaskFlow is really two programs that talk over HTTP.

┌─────────────────────────────┐ HTTP + JSON ┌─────────────────────────────┐ │ FRONTEND (the browser) │ ───────────────────────▶ │ BACKEND (the server) │ │ Next.js + React + Tailwind│ fetch() with a JWT token │ Spring Boot API │ │ http://localhost:3000 │ ◀─────────────────────── │ http://localhost:8080 │ │ folder: /frontend │ JSON responses │ /api/v1/... │ └─────────────────────────────┘ └──────────────┬──────────────┘ │ JPA / SQL ┌──────────▼──────────┐ │ PostgreSQL (Docker)│ │ localhost:5433 │ └─────────────────────┘
  • Frontend = what the user sees and clicks. It holds NO database access and NO secrets. It only knows how to call the API and render what comes back.
  • Backend = the brain + the data. It enforces the rules (auth, ownership) and is the only thing that touches the database.
Analogy

The frontend is the dining room (menus, tables, what the customer touches). The backend is the kitchen + storeroom (the cooking rules and the ingredients). They communicate through a serving hatch — that hatch is HTTP, and the language passed through it is JSON.

Part 2 — The four things that make the link work

2.1 CORS — the browser's permission slip

Browsers block a page on one origin (localhost:3000) from calling a different origin (localhost:8080) unless the server explicitly allows it. That permission is CORS.

Where we allow it config/CorsConfig.java
config.setAllowedOrigins(allowedOrigins);   // includes http://localhost:3000
config.setAllowedMethods(List.of("GET","POST","PUT","PATCH","DELETE","OPTIONS"));
config.setAllowedHeaders(List.of("*"));     // notably Authorization (our token)

Without this, every call from the frontend would fail in the browser with a CORS error — even though the API itself is fine. This is the #1 gotcha when a frontend "can't reach" a working backend.

2.2 JWT — the "I'm logged in" wristband

HTTP is stateless: the server forgets you between requests. So after login the server hands the browser a signed token (a JWT). The browser sends it back on every request to prove who it is.

1. User submits email+password ──▶ POST /api/v1/auth/login 2. Server verifies, returns a JWT ◀── { "token": "eyJ...", "user": {...} } 3. Frontend stores the token (localStorage) 4. Every later request carries it: Authorization: Bearer eyJ... 5. Server reads the token, knows the user, allows the request

2.3 The API client — the single bridge file

Instead of scattering fetch() calls everywhere, the frontend funnels them all through one helper. This is where the token gets attached and errors get unwrapped.

The bridge frontend/src/lib/api.ts
async function request<T>(path, options) {
  const headers = { ...options.headers };
  if (options.body) headers["Content-Type"] = "application/json";
  const token = getToken();                          // from localStorage
  if (token) headers["Authorization"] = `Bearer ${token}`;   // ← the link!
  const res = await fetch(`${BASE}${path}`, { ...options, headers });
  ...
}
export const apiToggleComplete = (id) =>
  request<Task>(`/tasks/${id}/complete`, { method: "PATCH" });

BASE = http://localhost:8080/api/v1. Every apiXxx() function maps 1:1 to a backend endpoint, so the frontend reads like a list of the API's capabilities.

2.4 The request/response cycle

A frontend action becomes an HTTP request, travels through the backend layers, and returns JSON the UI re-renders. Part 3 traces exactly that for one click.

Part 3 — One click, traced end-to-end

You click “Done” on a task. Here is every hop, with the real code at each.

#Where (file)What happens

2frontend/src/lib/api.tsrequest() attaches Authorization: Bearer <token> and does fetch(PATCH /tasks/{id}/complete).

The takeaway

Frontend → api.ts → (CORS) → filter → controller → service → repository → DB, then a DTO comes back. Every feature is this same pipeline. Learn it once; recognise it everywhere.

Part 4 — ⭐ How to spot Spring building blocks in the code

For each concept: the tell (what to look for), what it does, and where it lives in YOUR project.

CONTROLLER task/controller/TaskController.java
The tell: class annotated @RestController + @RequestMapping("/api/v1/..."), with methods marked @GetMapping/@PostMapping/@PutMapping/@PatchMapping/@DeleteMapping.

Does: the front door for HTTP. Maps a URL + verb to a method, reads the request, returns the response. Contains no business rules — it delegates to a service.

@RestController
@RequestMapping("/api/v1/tasks")          // ← every method's URL starts here
public class TaskController {
    @PatchMapping("/{id}/complete")        // ← PATCH /api/v1/tasks/{id}/complete
    public TaskResponse complete(@AuthenticationPrincipal UUID userId,
                                 @PathVariable UUID id) {
        return taskService.toggleComplete(userId, id);   // ← hands off to the service
    }
}

Also notice @AuthenticationPrincipal (the logged-in user's id), @PathVariable (part of the URL), @RequestBody (the JSON body), @RequestParam (query params like ?status=).

DTO (Data Transfer Object) task/dto/TaskRequest.java, TaskResponse.java
The tell: a Java record living in a dto/ package. No @Entity. Often has validation annotations (@NotBlank, @Size). It's the shape of the JSON in or out.

Does: defines exactly what the outside world sends/receives — deliberately separate from the database entity (so internal fields like a password hash can never leak).

public record TaskRequest(                 // ← "record" + dto package = a DTO
    @NotBlank @Size(max = 255) String title,   // ← validation rules
    String description,
    TaskStatus status, Priority priority,
    Instant dueDate, UUID categoryId
) {}

Rule of thumb: Request DTO = data coming IN; Response DTO = data going OUT. If it's a record and it's in dto/, it's a DTO.

ENTITY task/entity/Task.java, user/entity/User.java
The tell: class annotated @Entity + @Table(name="..."), fields with @Id, @Column, @ManyToOne. Lives in an entity/ package.

Does: one entity object = one row in a database table. This is the in-memory mirror of your data.

@Entity
@Table(name = "tasks")                     // ← maps to the 'tasks' table
public class Task {
    @Id @GeneratedValue(strategy = GenerationType.UUID)
    private UUID id;
    @Column(nullable = false) private String title;
    @ManyToOne(fetch = FetchType.LAZY) @JoinColumn(name = "owner_id")
    private User owner;                    // ← a relationship to another table
}

@ManyToOne = "many tasks belong to one user." That's a foreign key, expressed in Java.

REPOSITORY task/repository/TaskRepository.java
The tell: an interface (not a class!) that extends JpaRepository<Entity, IdType>. It has method signatures but no bodies — you never write the implementation.

Does: all database reads/writes. Spring generates the actual SQL at startup from the method names.

public interface TaskRepository
        extends JpaRepository<Task, UUID> {          // ← gives save/findById/delete free
    Optional<Task> findByIdAndOwnerId(UUID id, UUID ownerId);  // ← name → SQL WHERE
    long countByOwnerIdAndStatus(UUID ownerId, TaskStatus status);
}

"Derived query": Spring reads findByIdAndOwnerId and writes WHERE id=? AND owner_id=? for you. An interface extending JpaRepository is always a repository.

SERVICE task/service/TaskService.java
The tell: class annotated @Service, sitting in a service/ package, often with @Transactional methods. It injects repositories/mappers in its constructor.

Does: the business rules — the "brain." Validates ownership, applies defaults, coordinates repository calls. The controller calls it; it calls the repository.

@Service
public class TaskService {
    private final TaskRepository taskRepository;     // ← injected dependency
    public TaskService(TaskRepository taskRepository, ...) { ... }  // ← constructor injection

    @Transactional                                   // ← all-or-nothing DB unit
    public TaskResponse toggleComplete(UUID ownerId, UUID id) {
        Task task = getOwnedOrThrow(ownerId, id);    // ← the ownership RULE lives here
        ...
    }
}

If you're looking for "where does the actual logic happen?" — it's the @Service. Controllers are thin; services are where decisions are made.

MAPPER task/mapper/TaskMapper.java
The tell: a @Component in a mapper/ package with methods like toResponse(entity) that build a DTO from an entity.

Does: translates between Entity (DB shape) and DTO (wire shape) in one reusable place.

@Component
public class TaskMapper {
    public TaskResponse toResponse(Task task) {      // ← Entity in, DTO out
        return new TaskResponse(task.getId(), task.getTitle(), ...);
    }
}
CONFIG & @Bean config/PasswordEncoderConfig.java
The tell: class annotated @Configuration, with methods annotated @Bean.

Does: hands Spring a ready-made shared object (a "bean") to inject elsewhere. Used for things you don't write as @Service/@Component (often library types).

@Configuration
public class PasswordEncoderConfig {
    @Bean                                            // ← "store this object in the container"
    public PasswordEncoder passwordEncoder() { return new BCryptPasswordEncoder(); }
}
GLOBAL ERROR HANDLER common/exception/GlobalExceptionHandler.java
The tell: class annotated @RestControllerAdvice with methods annotated @ExceptionHandler(SomeException.class).

Does: one global "catch block" for the whole API. Any exception a controller throws lands here and becomes a tidy JSON error.

@RestControllerAdvice
public class GlobalExceptionHandler {
    @ExceptionHandler(ApiException.class)            // ← catches our NotFound/Conflict/etc.
    public ResponseEntity<ErrorResponse> handleApi(ApiException ex, HttpServletRequest req) { ... }
}
SPECIFICATIONS (dynamic filters) task/spec/TaskSpecifications.java
The tell: static methods returning Specification<Entity>, combined with Specification.allOf(...) in the service.

Does: builds WHERE-clause pieces at runtime so one endpoint supports many filter combinations (Phase 8).

public static Specification<Task> statusEquals(TaskStatus status) {
    if (status == null) return null;                 // ← absent filter = skipped
    return (root, query, cb) -> cb.equal(root.get("status"), status);
}
Dependency Injection — how to spot it everywhere

You'll see this pattern in every service/controller: a private final field + a constructor that receives it. You never see new TaskService(...). That's dependency injection: Spring creates one of each @Service/@Component/@Bean and passes them in automatically. When you see private final X x; set only in the constructor — that's an injected dependency.

Part 5 — How to read ANY feature (the recipe)

When you open a feature and feel lost, read its files in this order. Using tasks as the example:

StepLayerFileQuestion it answers
1Controllertask/controller/TaskController.javaWhat URLs exist? What goes in/out?
2DTOstask/dto/TaskRequest, TaskResponseWhat's the exact JSON shape?
3Servicetask/service/TaskService.javaWhat are the rules? (ownership, defaults, the toggle)
4Repositorytask/repository/TaskRepository.javaHow is the DB queried?
5Entitytask/entity/Task.javaWhat does one row look like + its relationships?
6Mappertask/mapper/TaskMapper.javaHow does an entity become the response DTO?
Why this order

You follow the same path a request takes. By the time you reach the entity, you already know why each field matters because you saw it used in the controller and service. Top-down beats reading files alphabetically.
